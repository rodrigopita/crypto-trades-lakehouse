# cp3: Candles reconcile with reality

Written 2026-11-17 from one session of the ingester and the processor's four queries, with a 60-second scripted reset and one run of the bad-trade injector, and from the reports `python -m reconciliation.bronze`, `python -m reconciliation.silver` and `python -m reconciliation.gold` write. It is the record of the cp3 done-criterion: the one-minute candles in Gold reconcile with Kraken's REST reference candles within a documented tolerance, accounting for the late-data policy. The quoted files are under `data/`, which git ignores.

## What the numbers say

- **38 of the 41 final candles match their reference candle within tolerance.** They hold 3,034 trades. Open, high, low, close and the trade count are exact in all 38, volume is at most 4.4e-15 off, and VWAP at most 0.0981.
- **The other three are accounted for.** 12:08 is partial. The subscribe snapshot reached back only to 12:08:33, so Gold has 23 of the minute's 75 trades. 12:23 and 12:24 are gap minutes, 13 trades short, all lost during the reset.
- **Three records agree on the 13 lost trades.** The Gold reconciliation counts 8 missing in 12:23 and 5 in 12:24. The Bronze reconciliation reports 13 missing trade ids, 116510941 to 116510953. Kraken's REST trades endpoint has all 13 ids, timed 12:23:38 to 12:24:04.
- **No trade was too late.** Every final candle's trade count equals Silver's count for its minute, and no Silver trade arrived with an event time older than one already received.
- **Every Bronze trade is still accounted for.** Bronze holds 3,318 trades, the same as the written-record log. 3,265 are in Silver, 2 were rejected and 51 dropped as duplicates.

## The late-data policy

Gold groups Silver's trades into one-minute windows of event time under a 1-minute watermark and appends each candle once. A candle is final when the watermark, the newest event time seen minus 1 minute, passes the end of its minute. Gold writes it then and never changes it. A trade that reaches Gold after its candle is final is too late, and that candle never counts it.

The threshold is 1 minute because nothing reaches Gold later than that. None of Silver's 8,566 trades in cp2's session arrived behind the newest event time of an earlier message, and none of the 3,265 in this one did. Reconnect snapshots do replay older trades, but those are duplicates, and Silver drops them under its own 5-minute watermark before Gold reads them.

The cost is the end of each session. Once the ingester stops, no newer trade moves the watermark past the last minutes, so Gold never writes their candles. Here that is 12:49 and 12:50, with 124 trades.

Delta's streaming sink has no update mode (`DELTA_UNSUPPORTED_OUTPUT_MODE`), so correcting a final candle would take a `foreachBatch` with a `MERGE`. With no late trade measured in either session, cp3 does without it.

## The tolerance

The Gold reconciliation walks every minute of the session, from Silver's first minute to the last final candle, and puts each one in one bucket. A minute with no Silver trades or no Gold candle counts 0 for that layer. The buckets are tested in this order:

| bucket     | test                                                    | fails the run                   |
| ---------- | ------------------------------------------------------- | ------------------------------- |
| unchecked  | no finished reference candle for the minute             | no                              |
| impossible | reference count below Silver's, or Gold's above Silver's | yes                             |
| partial    | the session's first minute in Silver                    | no                              |
| gap        | reference count above Silver's                          | no                              |
| too late   | Silver's count above Gold's                             | no                              |
| checked    | all three counts equal                                  | if a field is out of tolerance  |

A gap is trades that never reached the pipeline. Too late is the late-data policy at work. The run also fails when Gold has no final candle or no minute is checked, so a reconciliation run after Kraken's 12-hour window cannot pass on nothing. A checked minute with no trades anywhere has no candle, so its fields are not compared; Kraken reports such minutes, 8 of the 721 rows in the saved response.

Each field of a checked minute has its own tolerance:

| field                  | tolerance | why                                                                     | largest difference |
| ---------------------- | --------: | ----------------------------------------------------------------------- | -----------------: |
| open, high, low, close |     exact | Kraken writes one decimal, and that text parses to the double Gold holds |                  0 |
| volume                 |      1e-9 | Gold adds doubles; Kraken writes 8 decimals                             |            4.4e-15 |
| VWAP                   |       0.1 | Kraken cuts VWAP to one decimal                                         |             0.0981 |

All 38 VWAP differences put Gold above the reference, from 0.0018 to 0.0981. Rounding would put about half of them below. The same held for the 16 minutes of the morning's test run and for 4 minutes rebuilt from Kraken's own trades on 2026-11-16.

## How it was run

```sh
tar czf ~/crypto-trades-lakehouse-data-2026-11-17-gold-run.tgz data   # the morning's test run, 12:09:13
rm -rf data/*                                                          # keeps data/.gitkeep
mkdir data/session
docker compose up --build -d                                                       # 12:09:31
scripts/inject_failure.sh reset 60 | tee -a data/session/failures.log              # 12:23:35
uv run python -m scripts.inject_bad_trades 2>&1 | tee data/session/injection.log   # 12:33:20
docker compose stop ingester                                                       # 12:50:25
docker compose stop processor                                                      # killed 12:52:11
docker compose logs --no-color > data/session/compose.log
for r in bronze silver gold; do
    docker compose run --rm processor python -m reconciliation.$r 2>&1 \
        | tee data/session/reconciliation-$r.log
done                                                                               # 12:54 to 12:55
```

- **Code at `2569307`.** The Python files inside both images match that commit file for file, 5 in the ingester image and 11 in the processor image. Compose reused the containers of the morning's test run, so `compose.log` starts with that run at 11:43. Everything quoted here is from 12:09 on.
- **An empty start.** The processor created the empty Bronze table at 12:09:43 and the empty Silver trade and reject tables at 12:09:45 and 12:09:46, before the first landing file. Gold's first commit came at 12:09:55.
- **Ingester first.** Its SIGTERM handler flushed the open batch, 100 trades, at 12:50:25. Bronze committed that file at 12:50:27, Silver at 12:50:35 and Gold at 12:50:39, before the processor stopped.
- **Reconciliations after the processor stopped, each run twice.** All three only read: the Delta tables, the written-record log and Kraken's REST API. A second run of each at 13:19, read-only on the same `data/`, printed the same lines as the session's logs, apart from the reference window's start and end, which move with the clock. They are idempotent (safe to rerun: a second run of the same input changes nothing).
- **Kraken's answers, kept.** Kraken serves only the last 720 minutes, so from about 00:09 on 2026-11-18 it starts dropping this session's minutes. `data/session/reference-ohlc.json` is the OHLC response fetched in the 13:11 minute, with finished candles from 01:11 to 13:10. `data/session/reference-trades-around-reset.json` holds Kraken's 1,000 trades from 12:21:01 to 12:32:50, the ones that name the 13 lost ids.

## Fixed after the review

The two-axis review from `cp2-quality` found two holes in the reconciliation the session ran with, and `199608c` closed them:

- **A minute without a Gold candle fell in no bucket.** The reconciliation walked only Gold's minutes. A whole-minute outage leaves no Silver trades and no candle, and a minute whose every trade is too late leaves Silver trades but no candle, so both passed unseen. It now walks every minute of the session and counts a missing layer as 0, which makes the first a gap and the second too late.
- **An empty Gold passed.** It logged and exited 0. It now fails the run.

Three checks of `199608c`:

- **This session, against the saved response.** With `get_kraken_ohlc` reading `data/session/reference-ohlc.json` instead of Kraken, the reconciliation printed the session's lines: 41 candles, 12:08 partial, gaps of 8 and 5 in 12:23 and 12:24, nothing too late or impossible, and 38 checked minutes within tolerance.
- **This session, live, on 2026-11-18 at 02:41.** Kraken's window then started at 14:42 the day before, so all 41 minutes were unchecked and the run failed with `ReconciliationError`, exit 1.
- **Hand-made minutes.** A whole-minute outage came out as a gap with all 45 trades missing, a minute of 40 too-late trades as too late, a minute with no trades anywhere as checked with no fields compared, and a minute with more Silver trades than Kraken's and no candle as impossible.

## Findings

- **A 64-second outage lost 13 trades.** A snapshot is always 50 trades. In this session that reached back 59 s at the start, 36 s after the reset and 32 s after the unscripted drop, at about 80 trades a minute. A longer outage leaves a gap, and the Gold reconciliation names every minute it touches, including one it empties completely.
- **The connection dropped once on its own.** At 12:46:24, with no rule in place, it closed without a close frame, as it did in cp2 at 15:02:48. The ingester reconnected 1 s later, and all 50 snapshot trades were ones it already had, which Silver dropped.
- **No `MemoryManager` warnings.** cp2's processor logged 812 on the same 1 GiB heap. Those warnings come from Parquet reserving 128 MiB per open writer, and they named 8 to 10 writers. The likely reason they stopped is `2ac67c7`, which set `spark.sql.shuffle.partitions` to 2. The two stateful queries now write from 2 tasks each instead of up to 12 at once.
- **The processor still exits 137.** As in cp1 and cp2, it has no SIGTERM handler, so Compose kills it after the grace period. No data was harmed: the ingester had stopped 2 minutes earlier and the last commits were in.

## Left for later

- **Gap recovery.** The tolerance does not absorb a gap. The Gold reconciliation reports it and Bronze's gap count confirms it. A backfill from Kraken's REST trades endpoint would fill Bronze, but under a 1-minute watermark the backfilled trades would reach Gold too late for candles already final. Backfill waits until after cp4, if days remain.
- **The policy in the README, in cp4.** This document writes it down; the README gets one line.
- **A SIGTERM handler in the processor, in cp4.** It ends the exit 137.
- **Too-late trades measured, not derived, in cp4.** The reconciliation infers them from Silver's and Gold's counts. Gold's query reports `numRowsDroppedByWatermark` in its progress, which would count them directly.
- **Reconnects as metrics, in cp4.** This session had two, one of them unscripted, and they show only as log lines.
- **The reconciliation's timing.** As in cp2, it assumes the processor has stopped and every query has read the same Bronze. Nothing checks it.
- **One session per `data/`.** The partial minute is Silver's first minute, and the walk runs from there. On a `data/` holding two sessions, the pause between them would come out as gap minutes. Every session so far started from an empty `data/`.
- **Volume comparisons.** `docs/scope.md` asks for Gold metrics "such as VWAP and volume comparisons". Gold's volume is checked against Kraken's every minute; no other volume metric, such as buy against sell volume, is built.
- **Tests.** `tests/` still holds no file.
